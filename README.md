# CS-360-Mobile-Architect-Programming
Inventory Tracker Launch Plan
Inventory Tracker is an Android application I developed to give users a simple way to manage inventory items and their quantities. The application allows users to create an account, log in, add new inventory items, update item quantities, delete items, and receive optional SMS notifications when an item reaches a low-stock level. My goal was to keep the application simple and easy to use without adding features that were not necessary for the main purpose of the app. The application uses a SQLite database so user accounts and inventory information remain saved after the app is closed.
If Inventory Tracker were released in the Google Play Store, the app description would focus on the main features in simple language. I would explain that the app gives users a quick way to organize inventory, update quantities, and receive low-stock alerts. I would avoid filling the description with technical information because most users would care more about what the app can do than how it was built. For the app icon, I would use a simple image such as a storage box with a check mark. I would also use colors that match the blue and dark design of the application so the icon feels connected to the rest of the app.
The current project uses a minimum Android Software Development Kit level of 34 and targets Android Software Development Kit level 36. During development, I tested the app using a Pixel 8 emulator with API level 35. Before releasing the application publicly, I would test it on additional Android versions, screen sizes, and physical devices. New Android versions can affect permissions, security requirements, and application behavior, so I would continue testing the app whenever the target Android version is updated.
The main special permission required by Inventory Tracker is the SEND_SMS permission. This permission is used for the low-stock notification feature. The app asks the user for permission before SMS notifications are enabled. If permission is granted, the app can send a message when an inventory item reaches a quantity of two or less. If permission is denied, the rest of the app continues to work normally. The user can still log in, add items, update quantities, delete items, and view saved inventory. I tested both permission choices during development to make sure the application continued functioning correctly in either situation.
I would not request permissions that are unrelated to the app. Inventory Tracker does not need access to the camera, microphone, location, contacts, or photos. Limiting permissions helps keep the application focused and avoids asking users for unnecessary access to their devices.
For monetization, I would make the first version of Inventory Tracker free and would not include advertisements. I think advertisements could make a simple inventory application feel cluttered and could make it harder for users to quickly update information. A free version would also allow more people to try the app and provide feedback. If the application became more advanced in the future, I could consider offering optional premium features such as multiple inventory locations, exporting inventory data, backup and restore options, or more detailed reports. I would prefer an optional one-time upgrade instead of forcing advertisements into the application.
Before launch, I would complete a final test of the major features. During development, I tested account creation, duplicate usernames, incorrect and correct login information, inventory creation, viewing, updating, deleting, database persistence, SMS permission denial, SMS permission approval, low-stock notifications, and turning SMS notifications off. I also successfully generated an APK in Android Studio, which confirmed that the project compiled without build errors.
Overall, my launch plan for Inventory Tracker would focus on keeping the first release simple, reliable, and easy to understand. The main features are already working, and I would rather release a smaller application that works correctly than add unnecessary features that have not been fully tested. Future versions could add more advanced inventory tools based on user feedback while keeping the main purpose of the application clear and easy to use.

For this project, I developed an Android Inventory Tracker app. The goal was to let users create an account, log in, add inventory items, update quantities, delete items, and receive optional SMS alerts when inventory gets low. The app was designed to make basic inventory management simple and easy to understand.

The app needed a login screen, inventory screen, and SMS settings screen. I kept the interface simple so users could quickly see their inventory and access the most important actions without going through unnecessary screens. The inventory screen clearly separates the item name, quantity, and edit/delete actions.

When developing the app, I worked in smaller sections and tested each feature before moving on. I connected the UI to Java code, used SQLite for persistent user and inventory data, and added SMS permission handling. This approach helped me find problems faster and is something I plan to continue using in future projects.

I tested account creation, incorrect and correct login attempts, adding, editing, and deleting inventory, database persistence, SMS permission approval and denial, and low-stock alerts. Testing was important because it showed whether the app actually worked beyond just compiling successfully.

One challenge was turning the UI from Project Two into a fully working application. I had to figure out how to connect the inventory rows to real database data and make editing and deleting work dynamically. Breaking the problem into smaller parts helped me solve it.

I was especially successful with the inventory database and CRUD functionality. The app can create, read, update, and delete inventory items while keeping the data saved after the application is closed. This project gave me a much better understanding of how mobile UI design, Java code, databases, permissions, and testing all work together.
